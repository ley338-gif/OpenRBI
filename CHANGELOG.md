# Changelog

All notable changes to this project are documented in this file.

The format is loosely based on [Keep a Changelog](https://keepachangelog.com/), and this project does not yet follow semantic versioning (pre-alpha).

## [Unreleased]

### Added

- Project foundation: repository layout, initial documentation set, ADRs for the core architectural decisions, docker-compose skeleton, backend/session-agent/frontend scaffolding.
- Relational data model (§27 of the project brief) and Alembic migrations: `User`, `Role`, `Group`, `UserGroup`, `RecoveryCode`, `Policy`, `PolicyVersion`, `GroupPolicy`, `FilePolicyRule`, `BrowserSession`, `BrowserNode`, `QuarantineFile`, `Incident`, `SecurityEvent`. Default MVP roles (`USER`, `SECURITY_REVIEWER`, `ADMIN`) are seeded by migration.
- Local authentication: Argon2 password hashing, `POST /auth/login` / `POST /auth/logout` / `GET /auth/me`, server-side sessions in Redis (revocable, not JWTs), generic 401 on any login failure (no username enumeration), `USER_LOGIN`/`USER_LOGIN_FAILED` security events.
- TOTP MFA: QR-code enrollment (`POST /mfa/enroll`, `/mfa/enroll/confirm`), encrypted-at-rest secrets, one-time recovery codes (hashed, single-use), `POST /auth/mfa/verify` to complete a login, a brute-force attempt cap on the MFA challenge, and an admin-only `POST /mfa/admin/users/{id}/reset`. MFA is now enforced as mandatory for ADMIN/SECURITY_REVIEWER: those roles are forced through mandatory enrollment (`/mfa/setup/enroll` + `/mfa/setup/confirm`) before they ever receive a session, closing a gap where an unenrolled admin account could otherwise get a full session with no MFA at all.
- Admin user/group management: `POST/GET /admin/users`, disable/enable, admin password reset, role reassignment, group membership management, and `POST/GET /admin/groups` — all gated by a new `require_role()` dependency (403 fail-closed for non-admins). The mandatory-MFA-for-ADMIN/SECURITY_REVIEWER check from Phase 4 is re-evaluated from the user's *current* role at every login, so promoting a USER to SECURITY_REVIEWER correctly forces MFA enrollment on their very next login, not just at account creation. Five new `SecurityEventType` values (`USER_ROLE_CHANGED`, `USER_GROUPS_CHANGED`, `PASSWORD_RESET_BY_ADMIN`, `GROUP_CREATED`, `GROUP_DELETED`) extend the audit log beyond the project brief's minimum event list, since admin user/group management is equally security-relevant.
- Session Agent: `SandboxProvider` interface and its first implementation, `DockerSandboxProvider` (docs/adr/0003, 0010), exposed over the agent's internal token-authenticated API — create/start/isolate/restore/terminate (idempotent) plus status and live CPU/memory/PID metrics. Baseline container hardening (non-root, dropped capabilities, `no-new-privileges`, read-only rootfs, resource limits) is applied at creation. `isolate` disconnects the container from every attached network — a real, enforceable DENY-ALL network primitive — and `restore` reconnects it; both are verified end-to-end against the live Docker daemon. The agent only ever acts on containers it labeled itself, never on arbitrary host containers. `GET /v1/nodes/self` now reports real capacity/active-session-count/runtime-version instead of a stub.
- Browser sandbox image (`docker/browser/`, docs/adr/0006): Firefox ESR + Xvfb + x11vnc on `debian:bookworm-slim`, running as a fixed non-root uid, with an ephemeral per-session profile under tmpfs-mounted `/tmp` (never persisted, docs/adr/0007). Verified running under the exact hardening constraints `DockerSandboxProvider` applies (non-root, `cap-drop ALL`, `no-new-privileges`, read-only rootfs, memory/PID limits): rootfs write attempts correctly fail, Firefox starts and stays up, and x11vnc's RFB port is reachable from another container on the same network. `Firefox`'s own internal content-process sandbox is disabled (`MOZ_DISABLE_CONTENT_SANDBOX=1`) since it wants capabilities (unprivileged user namespaces) that conflict with the container-level hardening that is this platform's actual security boundary — documented, not a silent downgrade. Session Agent now defaults to this image instead of the Phase 6 `alpine` placeholder; full lifecycle (create/start/metrics/terminate) re-verified against it.
- noVNC remote display: a new `GET /v1/sandboxes/{id}/display` session-agent endpoint reports a sandbox's network address; a new authenticated backend WebSocket (`/display/{id}/ws`) relays raw RFB bytes between the end user's browser and that address (the backend still never touches Docker directly — this is a plain outbound TCP connection to a port the sandbox already exposes, not a privileged operation, per docs/adr/0005). The reverse proxy now passes WebSocket upgrades through for that path. A `@novnc/novnc`-based test harness (`frontend/src/SecureBrowserTest.tsx`) is wired into the frontend pending the real "start a session" flow in Phase 10/11. Verified fully end-to-end through the actual running stack: logged in via the real `/auth/login` flow, connected noVNC to a live sandbox through the reverse proxy, and confirmed genuine rendered Firefox UI on the canvas (149 distinct sampled colors, framebuffer dimensions matching the container's Xvfb screen) — not a blank frame.
- Network isolation: a dedicated, pinned-subnet `browser-plane` docker network (`172.30.0.0/24`, IPv6 disabled) now holds every browser sandbox, separate from `control-plane`; `scripts/setup-network-isolation.sh` enforces the project brief's full static IPv4 blocklist plus dynamically-discovered other-docker-networks and host-IP blocking on the Docker host's `DOCKER-USER` iptables chain. The backend is pinned to a static address (`172.30.0.2`) on `browser-plane` so it alone (of everything on that subnet) can still open new connections into it, for the Phase 8 display relay — every real sandbox can only receive `ESTABLISHED,RELATED` return traffic, never initiate a new connection into the control plane. Verified end-to-end against the live stack: public internet still reachable from a browser-plane container, Postgres/gateway/RFC1918/link-local all correctly blocked, sandbox-to-sandbox blocked, and the backend's own VNC relay still works. Caught two real bugs during that verification: the backend's own network leg was being caught by the same rules meant for sandboxes (fixed by pinning + exempting its address), and the audit `LOG` rules were silently never firing because they were ordered after their matching terminating `DROP` rule instead of before it.
- Session lifecycle: `POST /sessions` now really orchestrates a browser session end to end — per-user quota check, node selection (`select_node()`, the abstract scheduling seam from docs/architecture.md, upserting the single MVP `BrowserNode` row from the Session Agent's live self-report), sandbox create+start via the Session Agent, and a readiness wait before reporting the session `ACTIVE`. `GET /sessions/me`, `GET /sessions/{id}`, and `POST /sessions/{id}/terminate` are ownership-checked the same way as the display WebSocket — a session belonging to someone else is a 404, indistinguishable from a nonexistent one. The display WebSocket (Phase 8) now enforces real ownership via the `BrowserSession` row instead of trusting any session id, and drives the `ACTIVE ⇄ DISCONNECTED` transition from actual client connect/disconnect. The frontend's "Start Secure Browser" button drives this real flow instead of a manually-typed session id. Verified end-to-end through the actual UI (not just the API): clicking the button creates a session, connects noVNC, and renders real Firefox UI (145 distinct sampled canvas colors); a second click while one session is active correctly surfaces `429 Too Many Requests` in the UI; ending the session terminates the sandbox with no orphaned containers.

- Admin session control: `POST /admin/sessions/{id}/{disconnect,isolate,restore,kill}`, backed by the real Docker-level primitives from Phase 6 (isolate actually disconnects the sandbox's network; kill actually removes the container) via the same `app/services/sessions.py` module Phase 10 introduced. `GET /admin/sessions` and `GET /admin/users/{id}/sessions` give admin/reviewer visibility. Disconnect and Isolate are available to both ADMIN and SECURITY_REVIEWER (matching §6's explicit reviewer isolate right); Kill is ADMIN-only — the project brief doesn't state which role each of the three needs, so this follows the project's own "pick the more restrictive reading when ambiguous" principle, documented in docs/session-lifecycle.md. An admin-triggered Isolate always opens an Incident (not just a security event), matching the Definition-of-Done walkthrough's step 25. Admin-forced Disconnect closes the user's live display connection immediately via a new in-process WebSocket registry, not just a database flag the client wouldn't notice.

  Verified end-to-end against the real running stack: a plain USER gets 403 on every `/admin/sessions` endpoint; an admin isolates a session and the Incident + `SESSION_ISOLATED` event both land; a SECURITY_REVIEWER can restore that same session but gets 403 attempting to kill it; the admin then kills it, idempotently, with the sandbox actually destroyed (confirmed via `docker ps`) and a distinct `SESSION_TERMINATED` event recorded for that specific action.

- Policy engine: full draft → publish → rollback workflow (`/admin/policies/*`) with immutable published versions (editing one is a `409`, not silently allowed), and a deterministic file-decision evaluator (`app/services/policy_engine.py`) implementing the project brief's conflict model (`DENY` > `QUARANTINE` > `AUTO_RELEASE` > fail-closed `QUARANTINE` default when nothing matches). Source-hostname matching (`app/core/source_matching.py`) is structural, not substring-based — `*.microsoft.com` matches `download.microsoft.com` and `microsoft.com` itself but never `microsoft.com.attacker.org` or `evil-microsoft.com`. Every decision records which `PolicyVersion` actually produced it. Verified with the exact adversarial domain-matching cases from the project brief, plus the full lifecycle: two groups with conflicting rules on the same user correctly resolve to `DENY`; an unmatched file type correctly fails closed to `QUARANTINE`; rolling back a policy to an older published version actually changes which rule set governs a live decision.

- Download interception (docs/quarantine.md): Firefox is now configured (`docker/browser/entrypoint.sh`) to silently auto-save downloads to a fixed directory. The Session Agent gained `GET/DELETE /v1/sandboxes/{id}/downloads*` endpoints reading through `exec` (not the Docker archive API — see Fixed, below), and the backend runs a per-session background poller (`app/core/download_poller.py`) that fetches each new completed download, hashes it, detects its real MIME type via magic bytes (never the extension), recovers a best-effort origin URL via Firefox's `user.xdg.origin.url` xattr, runs it through the Phase 12 policy engine as a pre-check, stages it content-addressed by SHA-256, and records a `QuarantineFile` row (`PENDING_SCAN`) plus a `DOWNLOAD_REQUESTED` event. Every file stays `PENDING_SCAN` — no scanner exists yet (Phase 14), so nothing is ever auto-released here. Verified end-to-end against the live stack, driven by the actual background poller (not a one-off manual call): a file named `report.txt` containing PNG magic bytes was correctly detected as not `text/plain`, and a file tagged with a simulated Firefox origin-URL xattr had its URL/hostname/TLS metadata correctly extracted.

- File scanner (docs/quarantine.md#scanning-and-the-final-decision-phase-14): `app/core/clamav_client.py` speaks clamd's native protocol directly over TCP (never trusted to a third-party client library) for `PING`/`VERSION`/`INSTREAM`. `app/services/scanning.py` applies the full fail-closed decision matrix from [ADR 0008](docs/adr/0008-fail-closed.md): scanner unreachable → `QUARANTINED` regardless of policy; infected → `QUARANTINED` + `MALWARE_DETECTED` event + a `CRITICAL` Incident (never silently deleted); clean + `DENY` → `REJECTED` immediately; clean + `QUARANTINE`/unmatched → `QUARANTINED`; clean + `AUTO_RELEASE` → `RELEASED`. Verified against the live stack with the standard EICAR test string (correctly flagged `Eicar-Test-Signature`, forced to `QUARANTINED` with a `CRITICAL` incident *even when its own policy verdict was `AUTO_RELEASE`* — malware detection overrides policy, never the reverse) and by actually stopping the ClamAV container and confirming an otherwise-auto-releasable file correctly fails closed instead.

- Quarantine review and release (docs/quarantine.md#review-and-release-phase-15): `POST /admin/quarantine/{id}/{release,reject}` for ADMIN/SECURITY_REVIEWER (§6's explicit reviewer right), only ever actionable on a still-`QUARANTINED` file — re-releasing or rejecting an already-decided file is a `409`, not silently accepted. Every decision records who/when/why and emits `FILE_RELEASED`/`FILE_REJECTED`. `app/core/release_tokens.py` issues single-use, 5-minute download tokens via Redis `GETDEL` (atomic get-and-delete — no window for two concurrent requests to both consume the same token); `GET /files/download/{token}` requires both a valid token and that the requester's session matches its owner, failing identically (generic `401`) for unknown/expired/reused/wrong-owner tokens. `GET /files/me` and the token-request endpoint use the same ownership pattern as sessions/display: someone else's file is a `404`, not a `403` — verified even against an ADMIN account, which gets no implicit ownership. Verified end-to-end against the live stack: reviewer release/reject, a rejected double-release (`409`), a blocked plain USER (`403`), a full token-issue → download → reuse-fails (`401`) cycle, and a different user (including an admin) correctly denied a token for someone else's file (`404`).

- Upload pipeline (docs/quarantine.md#upload-pipeline-phase-16): `POST /sessions/{id}/uploads` — hash, real MIME detection, the Phase 12 policy engine, a real ClamAV scan, then a write into the sandbox via the Session Agent, in that order and only if every step passes. No local client directory is ever mounted into a sandbox. Deliberately simpler than downloads: uploads have no `QUARANTINED`-and-await-review state — both `QUARANTINE` and `DENY` policy verdicts block immediately (`UPLOAD_BLOCKED`), since the user is actively waiting on the action; an infected upload is never written and gets a `CRITICAL` Incident, and a scanner outage blocks everything regardless of policy, matching the download pipeline's fail-closed guarantees. Two new `SecurityEventType` values (`UPLOAD_REQUESTED`, `UPLOAD_BLOCKED`) added via migration.

- Incident management (docs/admin-guide.md#incidents-phase-17): `GET/PUT /admin/incidents*` for ADMIN/SECURITY_REVIEWER (§6's explicit reviewer right). A new aggregator (`app/services/incidents.py`) opens a `HIGH` "Repeated policy violations" incident once a user crosses 3 blocked downloads/uploads within 15 minutes — deliberately not one incident per blocked transfer (§21 explicitly warns against this), and deduplicated so a user already under an open incident for this doesn't get a second one for further attempts. Verified end-to-end: 3 blocked uploads open exactly one incident, a 4th blocked upload doesn't open a second; a reviewer lists/views/transitions it through `INVESTIGATING` → `RESOLVED` with a resolution note; an invalid status value is a clean `400`; a plain USER is blocked (`403`).

- Audit/Security Events (docs/api.md#audit--security-events-phase-18): a review/completeness pass, not new event plumbing (that's been flowing correctly since Phase 3). Verified codebase-wide that `SecurityEvent` rows are only ever constructed inside `record_security_event` (nothing bypasses it), that nothing anywhere issues an `UPDATE`/`DELETE` against the table (append-only is enforced by that absence), and that every `metadata_json` payload across every call site is limited to IDs/hashes/filenames/reason strings — never a password, secret, token, or file content. Added `GET /admin/security-events` (filterable, paginated) for ADMIN/SECURITY_REVIEWER — the admin portal had no way to actually read the audit trail before this. This pass also surfaced and closed two real gaps: `GROUP_DELETED` and `NODE_DRAINED` were defined enum values with no code anywhere that could ever emit them, because the underlying admin features (delete a group, drain a node) didn't exist. Added `DELETE /admin/groups/{id}` and `POST /admin/nodes/{id}/{drain,undrain}`.

### Fixed
- A quota-exceeded session-create attempt was mapped to `502 Bad Gateway` instead of a proper client error — added a dedicated `QuotaExceededError` mapped to `429 Too Many Requests`.
- `BrowserNode` identity was keyed on the Session Agent container's own OS hostname, which is ephemeral and changes on every container recreation — every rebuild during this project's own testing silently orphaned a new `BrowserNode` row instead of updating the existing one (5 accumulated ghost rows found during this pass). Worse, draining a node had no actual effect on scheduling, because the drained row usually wasn't the one `select_node()` was actually looking up anymore. Fixed by giving the Session Agent a configured, stable `node_name` instead of using `socket.gethostname()`.
- Two real, previously-latent bugs in the async database session layer, both surfaced only once Phase 17 happened to make several sequential requests that touched the connection pool and an `onupdate`-triggered column in close succession: (1) `pool_pre_ping=True` is a known-broken combination with SQLAlchemy's async engine — its connection health-check can run outside the greenlet context the async dialect needs, raising `MissingGreenlet`. Replaced with `pool_recycle`, which proactively discards aging connections instead without that failure mode. (2) `Incident.updated_at` has a server-side `ON UPDATE` trigger, which SQLAlchemy marks expired after any flush that touches the row regardless of `expire_on_commit` — a bare attribute access in a response-serialization helper right after `commit()` triggered an implicit lazy-load SELECT outside the async bridge, same `MissingGreenlet` symptom. Fixed with an explicit `await db.refresh()` before serializing. No other response schema currently exposes an `onupdate` column the same way, but this is worth remembering before adding one.
- The Session Agent's write-into-sandbox path (`write_upload`) hit the same tmpfs/archive-API incompatibility Phase 13 found on the read side, plus a second bug: `exec_inspect`'s reported exit code stayed `None` well after the write had actually completed correctly — a plain socket `close()` doesn't reliably signal EOF to the remote process's stdin in time. Fixed by explicitly shutting down the write half of the socket first, and, since the exit code still couldn't always be trusted, independently verifying the write via the file's actual size on disk.
- Docker's archive API (`get_archive`/`docker cp`) cannot read files from a tmpfs mount — confirmed empirically (even a plain `docker cp` from the host failed for a file that unmistakably existed) — since it reads through the storage driver's layer-diff mechanism, and the sandbox's download directory lives under the tmpfs-mounted `/tmp`. Switched the Session Agent's download-fetch to `exec` (`cat`), which reads through a live process in the container's own mount namespace instead.
- `getfattr`'s informational stderr message ("Removing leading '/'...") was getting silently concatenated onto the actual extended-attribute value with no separator, since `exec_run` combines stdout and stderr by default — corrupting the recovered origin URL. Fixed by explicitly redirecting stderr away.
- A background poller task started via a one-off test script died the instant that script's process exited, since `asyncio.create_task` doesn't keep a task alive past its creating event loop closing — the poller only works when a session is created through the actual long-lived server process. Not an application bug, but a real trap for testing background-task-driven features.
- The frontend tried to connect noVNC immediately after `POST /sessions` returned, but the sandbox's VNC server needs a moment after container start to actually begin listening — an intermittent real race condition caught during end-to-end UI testing, not just a theoretical one. Session creation now polls the display port with a bounded retry before reporting the session `ACTIVE`.
- nginx caches the resolved IP of `proxy_pass` upstreams (`backend`, `frontend`) at worker-process start; recreating those containers (e.g. via `docker compose up --build`) without restarting `reverse-proxy` left it pointing at stale, now-dead IPs, causing a `502` on every request. Documented in docs/troubleshooting.md — restart `reverse-proxy` after rebuilding `backend` or `frontend`.

### Fixed

- `clamav/clamav:1.3` in `docker-compose.yml` did not exist upstream; pinned to `1.5.4`.
- Several nullable timestamp columns (`recovery_codes.used_at`, `users.disabled_at`, `browser_sessions.started_at`/`ended_at`/`last_activity_at`, `browser_nodes.last_heartbeat`, `policy_versions.published_at`, `quarantine_files.reviewed_at`) were timezone-naive while application code writes timezone-aware datetimes everywhere; this crashed the first time any of them was actually written to. Migrated all of them to `TIMESTAMP WITH TIME ZONE`.
