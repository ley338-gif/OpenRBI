# Changelog

All notable changes to this project are documented in this file.

The format is loosely based on [Keep a Changelog](https://keepachangelog.com/). The repository is preparing its first semantic versioned release candidate; until a version is tagged, changes remain under `Unreleased`.

## [Unreleased]

### Security

- LDAP/LDAPS: certificate verification is now explicitly enforced (`OPT_X_TLS_REQUIRE_CERT=demand`) rather than relying on the OS/OpenLDAP default, and a custom CA bundle can be configured via `OPENRBI_LDAP_CA_CERT_FILE` for directories using an internal/private CA (RBI-POST-001).
- Added CSRF protection (signed double-submit cookie) as a second, independent layer alongside `SameSite=Lax` on the session cookie — every state-changing request now requires a matching `X-CSRF-Token` header, enforced by new middleware covering every listener mode and both portals via the shared `ApiClient`. Requires a new `OPENRBI_CSRF_SECRET_KEY` secret (RBI-POST-003).
- Fixed a check-then-update race in MFA recovery code redemption (`SELECT ... FOR UPDATE`) — two concurrent requests replaying the same single-use recovery code could previously both succeed (RBI-POST-015).
- `GET /admin/ldap/config` (a sensitive config disclosure) is now audited (`LDAP_CONFIG_READ`), matching every other LDAP configuration action (RBI-POST-017).

### Documentation

- Backup and restore docs now explicitly state that `./scripts/backup.sh` does not include `.env` (most critically `OPENRBI_TOTP_SECRET_ENCRYPTION_KEY`) or TLS certificates/keys, and what restoring without them does to existing MFA enrollments (RBI-POST-005).

### Operations

- Added a `network_isolation` component to `/admin` system health, reporting `NOT_CONFIGURED`/`DEGRADED`/`HEALTHY` based on a marker file `scripts/setup-network-isolation.sh` now writes — surfaces a visible warning when the required host-level iptables isolation has never been applied or hasn't been reconfirmed recently, instead of the stack silently appearing fully healthy either way. Provided `scripts/systemd/openrbi-network-isolation.{service,timer}` to reapply it automatically after host reboots (RBI-POST-002).

## [1.0.0] - 2026-08-15

### Security

- Made password-bearing local identities authoritative over same-named LDAP identities, closing a collision path that could otherwise authenticate a local privileged role with a directory password.
- Added a persisted, configurable 30-minute expiry for the console-issued first-run setup token.
- Centralized session-cookie issuance/removal and added coverage for `Secure`, `HttpOnly`, `SameSite=Lax`, path, max-age, and server-side expiry.
- Expanded the live security gate across sandbox hardening, control-plane reachability, IPv6 bypass prevention, benign/EICAR/outage file outcomes, upload fail-closed behavior, complete-history secret scanning, and frontend bundle secret checks.

### Fixed

- Fault-injection reliability: hard-killed or startup-interrupted browser containers are now discovered even when stopped, removed before their DB session is finalized as failed, retried if cleanup is temporarily unavailable, audited with explicit lost/start-failure events, and surfaced as Admin Dashboard warnings. A required destructive CI acceptance now exercises Browser/Agent/backend/PostgreSQL/Valkey/ClamAV failures, orphan cleanup, startup interruption, Drain, Maintenance, and control-plane network loss.

- V1-005 reproducible dependencies: backend and Session Agent production/dev dependency graphs are now committed as exact, hash-verified Linux/Python 3.11 lockfiles. Production images, integration runners, and `pip-audit` consume those locks; CI rejects stale Python locks. The frontend image now uses the committed workspace lock through `npm ci`. The pinned regeneration and review procedure is documented in `docs/release/dependencies.md`.
- V1-001 LDAP CI stability: the HTTP-level LDAP runner no longer rewrites `.env` or invokes `docker compose up -d --build backend` mid-test. The latter was the exact command returning exit 137 in main CI; the available logs do not establish `OOMKilled`, so the failure is not labelled as OOM. The suite now starts a short-lived LDAP-enabled backend from the already-built Compose image, preserves the normal stack, emits backend logs on readiness failure, and removes both throwaway containers on every exit.
- V1-002 release gates: CI now lint-checks all shipped Python code, tests, and migrations with Ruff; type-checks backend and Session Agent independently with mypy; audits resolved production dependencies for both Python components with `pip-audit`; and exposes a single fail-closed `Release gates` result that succeeds only when every required build, scan, integration, security, LDAP, lint, and type-check job succeeded. The authoritative gate mapping is documented in `docs/release/release-gates.md`.

Five new `SecurityEventType` values (`USER_ROLE_CHANGED`, `USER_GROUPS_CHANGED`, `PASSWORD_RESET_BY_ADMIN`, `GROUP_CREATED`, `GROUP_DELETED`) extend the audit log beyond the project brief's minimum event list, since admin user/group management is equally security-relevant.

Baseline container hardening (non-root, dropped capabilities, `no-new-privileges`, read-only rootfs, resource limits) is applied at creation. `isolate` disconnects the container from every attached network — a real, enforceable DENY-ALL network primitive — and `restore` reconnects it; both are verified end-to-end against the live Docker daemon. The agent only ever acts on containers it labeled itself, never on arbitrary host containers. `GET /v1/nodes/self` now reports real capacity/active-session-count/runtime-version instead of a stub.

Verified running under the exact hardening constraints `DockerSandboxProvider` applies (non-root, `cap-drop ALL`, `no-new-privileges`, read-only rootfs, memory/PID limits): rootfs write attempts correctly fail, Firefox starts and stays up, and x11vnc's RFB port is reachable from another container on the same network. `Firefox`'s own internal content-process sandbox is disabled (`MOZ_DISABLE_CONTENT_SANDBOX=1`) since it wants capabilities (unprivileged user namespaces) that conflict with the container-level hardening that is this platform's actual security boundary — documented, not a silent downgrade. Session Agent now defaults to this image instead of the Phase 6 `alpine` placeholder; full lifecycle (create/start/metrics/terminate) re-verified against it.
- noVNC remote display: a new `GET /v1/sandboxes/{id}/display` session-agent endpoint reports a sandbox's network address; a new authenticated backend WebSocket (`/display/{id}/ws`) relays raw RFB bytes between the end user's browser and that address (the backend still never touches Docker directly — this is a plain outbound TCP connection to a port the sandbox already exposes, not a privileged operation, per docs/adr/0005). The reverse proxy now passes WebSocket upgrades through for that path. A `@novnc/novnc`-based test harness (`frontend/src/SecureBrowserTest.tsx`) is wired into the frontend pending the real "start a session" flow in Phase 10/11. - Network isolation: a dedicated, pinned-subnet `browser-plane` docker network (`172.30.0.0/24`, IPv6 disabled) now holds every browser sandbox, separate from `control-plane`; `scripts/setup-network-isolation.sh` enforces the project brief's full static IPv4 blocklist plus dynamically-discovered other-docker-networks and host-IP blocking on the Docker host's `DOCKER-USER` iptables chain. The backend is pinned to a static address (`172.30.0.2`) on `browser-plane` so it alone (of everything on that subnet) can still open new connections into it, for the Phase 8 display relay — every real sandbox can only receive `ESTABLISHED,RELATED` return traffic, never initiate a new connection into the control plane. Verified end-to-end against the live stack: public internet still reachable from a browser-plane container, Postgres/gateway/RFC1918/link-local all correctly blocked, sandbox-to-sandbox blocked, and the backend's own VNC relay still works. Caught two real bugs during that verification: the backend's own network leg was being caught by the same rules meant for sandboxes (fixed by pinning + exempting its address), and the audit `LOG` rules were silently never firing because they were ordered after their matching terminating `DROP` rule instead of before it.
- Session lifecycle: `POST /sessions` now really orchestrates a browser session end to end — per-user quota check, node selection (`select_node()`, the abstract scheduling seam from docs/architecture.md, upserting the single MVP `BrowserNode` row from the Session Agent's live self-report), sandbox create+start via the Session Agent, and a readiness wait before reporting the session `ACTIVE`. `GET /sessions/me`, `GET /sessions/{id}`, and `POST /sessions/{id}/terminate` are ownership-checked the same way as the display WebSocket — a session belonging to someone else is a 404, indistinguishable from a nonexistent one. The display WebSocket (Phase 8) now enforces real ownership via the `BrowserSession` row instead of trusting any session id, and drives the `ACTIVE ⇄ DISCONNECTED` transition from actual client connect/disconnect. The frontend's "Start Secure Browser" button drives this real flow instead of a manually-typed session id. Verified end-to-end through the actual UI (not just the API): clicking the button creates a session, connects noVNC, and renders real Firefox UI (145 distinct sampled canvas colors); a second click while one session is active correctly surfaces `429 Too Many Requests` in the UI; ending the session terminates the sandbox with no orphaned containers.

- Admin session control: `POST /admin/sessions/{id}/{disconnect,isolate,restore,kill}`, backed by the real Docker-level primitives from Phase 6 (isolate actually disconnects the sandbox's network; kill actually removes the container) via the same `app/services/sessions.py` module Phase 10 introduced. `GET /admin/sessions` and `GET /admin/users/{id}/sessions` give admin/reviewer visibility. Disconnect and Isolate are available to both ADMIN and SECURITY_REVIEWER (matching §6's explicit reviewer isolate right); Kill is ADMIN-only — the project brief doesn't state which role each of the three needs, so this follows the project's own "pick the more restrictive reading when ambiguous" principle, documented in docs/session-lifecycle.md. An admin-triggered Isolate always opens an Incident (not just a security event), matching the Definition-of-Done walkthrough's step 25. Admin-forced Disconnect closes the user's live display connection immediately via a new in-process WebSocket registry, not just a database flag the client wouldn't notice.

  Verified end-to-end against the real running stack: a plain USER gets 403 on every `/admin/sessions` endpoint; an admin isolates a session and the Incident + `SESSION_ISOLATED` event both land; a SECURITY_REVIEWER can restore that same session but gets 403 attempting to kill it; the admin then kills it, idempotently, with the sandbox actually destroyed (confirmed via `docker ps`) and a distinct `SESSION_TERMINATED` event recorded for that specific action.

- Policy engine: full draft → publish → rollback workflow (`/admin/policies/*`) with immutable published versions (editing one is a `409`, not silently allowed), and a deterministic file-decision evaluator (`app/services/policy_engine.py`) implementing the project brief's conflict model (`DENY` > `QUARANTINE` > `AUTO_RELEASE` > fail-closed `QUARANTINE` default when nothing matches). Source-hostname matching (`app/core/source_matching.py`) is structural, not substring-based — `*.microsoft.com` matches `download.microsoft.com` and `microsoft.com` itself but never `microsoft.com.attacker.org` or `evil-microsoft.com`. Every decision records which `PolicyVersion` actually produced it. Verified with the exact adversarial domain-matching cases from the project brief, plus the full lifecycle: two groups with conflicting rules on the same user correctly resolve to `DENY`; an unmatched file type correctly fails closed to `QUARANTINE`; rolling back a policy to an older published version actually changes which rule set governs a live decision.

- Download interception (docs/quarantine.md): Firefox is now configured (`docker/browser/entrypoint.sh`) to silently auto-save downloads to a fixed directory. The Session Agent gained `GET/DELETE /v1/sandboxes/{id}/downloads*` endpoints reading through `exec` (not the Docker archive API — see Fixed, below), and the backend runs a per-session background poller (`app/core/download_poller.py`) that fetches each new completed download, hashes it, detects its real MIME type via magic bytes (never the extension), recovers a best-effort origin URL via Firefox's `user.xdg.origin.url` xattr, runs it through the Phase 12 policy engine as a pre-check, stages it content-addressed by SHA-256, and records a `QuarantineFile` row (`PENDING_SCAN`) plus a `DOWNLOAD_REQUESTED` event. Every file stays `PENDING_SCAN` — no scanner exists yet (Phase 14), so nothing is ever auto-released here. Verified end-to-end against the live stack, driven by the actual background poller (not a one-off manual call): a file named `report.txt` containing PNG magic bytes was correctly detected as not `text/plain`, and a file tagged with a simulated Firefox origin-URL xattr had its URL/hostname/TLS metadata correctly extracted.

- File scanner (docs/quarantine.md#scanning-and-the-final-decision-phase-14): `app/core/clamav_client.py` speaks clamd's native protocol directly over TCP (never trusted to a third-party client library) for `PING`/`VERSION`/`INSTREAM`. `app/services/scanning.py` applies the full fail-closed decision matrix from [ADR 0008](docs/adr/0008-fail-closed.md): scanner unreachable → `QUARANTINED` regardless of policy; infected → `QUARANTINED` + `MALWARE_DETECTED` event + a `CRITICAL` Incident (never silently deleted); clean + `DENY` → `REJECTED` immediately; clean + `QUARANTINE`/unmatched → `QUARANTINED`; clean + `AUTO_RELEASE` → `RELEASED`. Verified against the live stack with the standard EICAR test string (correctly flagged `Eicar-Test-Signature`, forced to `QUARANTINED` with a `CRITICAL` incident *even when its own policy verdict was `AUTO_RELEASE`* — malware detection overrides policy, never the reverse) and by actually stopping the ClamAV container and confirming an otherwise-auto-releasable file correctly fails closed instead.

- Quarantine review and release (docs/quarantine.md#review-and-release-phase-15): `POST /admin/quarantine/{id}/{release,reject}` for ADMIN/SECURITY_REVIEWER (§6's explicit reviewer right), only ever actionable on a still-`QUARANTINED` file — re-releasing or rejecting an already-decided file is a `409`, not silently accepted. Every decision records who/when/why and emits `FILE_RELEASED`/`FILE_REJECTED`. `app/core/release_tokens.py` issues single-use, 5-minute download tokens via Redis `GETDEL` (atomic get-and-delete — no window for two concurrent requests to both consume the same token); `GET /files/download/{token}` requires both a valid token and that the requester's session matches its owner, failing identically (generic `401`) for unknown/expired/reused/wrong-owner tokens. `GET /files/me` and the token-request endpoint use the same ownership pattern as sessions/display: someone else's file is a `404`, not a `403` — verified even against an ADMIN account, which gets no implicit ownership. Verified end-to-end against the live stack: reviewer release/reject, a rejected double-release (`409`), a blocked plain USER (`403`), a full token-issue → download → reuse-fails (`401`) cycle, and a different user (including an admin) correctly denied a token for someone else's file (`404`).

- Upload pipeline (docs/quarantine.md#upload-pipeline-phase-16): `POST /sessions/{id}/uploads` — hash, real MIME detection, the Phase 12 policy engine, a real ClamAV scan, then a write into the sandbox via the Session Agent, in that order and only if every step passes. No local client directory is ever mounted into a sandbox. Deliberately simpler than downloads: uploads have no `QUARANTINED`-and-await-review state — both `QUARANTINE` and `DENY` policy verdicts block immediately (`UPLOAD_BLOCKED`), since the user is actively waiting on the action; an infected upload is never written and gets a `CRITICAL` Incident, and a scanner outage blocks everything regardless of policy, matching the download pipeline's fail-closed guarantees. Two new `SecurityEventType` values (`UPLOAD_REQUESTED`, `UPLOAD_BLOCKED`) added via migration.

- Incident management (docs/admin-guide.md#incidents-phase-17): `GET/PUT /admin/incidents*` for ADMIN/SECURITY_REVIEWER (§6's explicit reviewer right). A new aggregator (`app/services/incidents.py`) opens a `HIGH` "Repeated policy violations" incident once a user crosses 3 blocked downloads/uploads within 15 minutes — deliberately not one incident per blocked transfer (§21 explicitly warns against this), and deduplicated so a user already under an open incident for this doesn't get a second one for further attempts. Verified end-to-end: 3 blocked uploads open exactly one incident, a 4th blocked upload doesn't open a second; a reviewer lists/views/transitions it through `INVESTIGATING` → `RESOLVED` with a resolution note; an invalid status value is a clean `400`; a plain USER is blocked (`403`).

- Audit/Security Events (docs/api.md#audit--security-events-phase-18): a review/completeness pass, not new event plumbing (that's been flowing correctly since Phase 3). Verified codebase-wide that `SecurityEvent` rows are only ever constructed inside `record_security_event` (nothing bypasses it), that nothing anywhere issues an `UPDATE`/`DELETE` against the table (append-only is enforced by that absence), and that every `metadata_json` payload across every call site is limited to IDs/hashes/filenames/reason strings — never a password, secret, token, or file content. Added `GET /admin/security-events` (filterable, paginated) for ADMIN/SECURITY_REVIEWER — the admin portal had no way to actually read the audit trail before this. This pass also surfaced and closed two real gaps: `GROUP_DELETED` and `NODE_DRAINED` were defined enum values with no code anywhere that could ever emit them, because the underlying admin features (delete a group, drain a node) didn't exist. Added `DELETE /admin/groups/{id}` and `POST /admin/nodes/{id}/{drain,undrain}`.

- Health monitoring (§25, docs/architecture.md#health-monitoring-phase-19): new `GET /admin/health` for ADMIN/SECURITY_REVIEWER (`app/services/health.py`), checking every dependency named in the project brief independently and non-fatally — API, PostgreSQL (`SELECT 1`), Redis (`PING`), Session Agent (its `/v1/nodes/self` self-report), sandbox runtime and browser-image availability (both surfaced through that same Session Agent call — a new `sandbox_image_available()` provider method actually checks the image is present via the Docker API, since it's built separately by `scripts/build-browser-image.sh` rather than by `docker compose up` and a deployment can genuinely be missing it), ClamAV (`PING`/`VERSION`), and quarantine-storage writability (a real write+delete probe against the staging directory, not just an `os.path.exists`). One dependency failing never takes another's check down or 500s the endpoint. The existing unauthenticated `GET /health` stays a pure liveness probe on purpose: since `/admin/health` needs a DB-backed session to authenticate, it — like every other admin endpoint — is unreachable during a full PostgreSQL outage, so ops always has the plain liveness probe as the one thing guaranteed to answer regardless of dependency state. Verified end-to-end against the live stack, including deliberately stopping ClamAV (`DEGRADED`, `clamav: UNAVAILABLE`), stopping the Session Agent (`DEGRADED`, `session_agent`/`sandbox_runtime`/`browser_image` all `UNAVAILABLE`), and stopping PostgreSQL (confirmed `/admin/health` correctly becomes unreachable like any other admin endpoint, while `/health` still returns `200 ok`).

- Hardening (docs/security-model.md#control-plane-container-hardening-phase-20): every static `docker-compose.yml` service now gets `no-new-privileges`; `backend` and `session-agent` (the code-we-wrote services) additionally get all Linux capabilities dropped, and `session-agent` — the one component with Docker-socket access — drops from root to a non-root UID (`10001`, kept in group `0` since `docker.sock` is typically group-readable/writable as `root`). `frontend`/`reverse-proxy` (nginx) drop all capabilities except `NET_BIND_SERVICE`/`CHOWN`/`SETUID`/`SETGID`, and `docker/nginx/nginx.conf` now declares `user nginx;` — without it nginx never actually dropped its worker processes to an unprivileged user at all, the opposite of hardening. `postgres`/`redis`/`clamav` (vendor images) get `no-new-privileges` only; `cap_drop` was deliberately not risked against their own root-requiring startup sequences. `backend`/`session-agent` `Settings` now reject, at startup, any critical secret that's empty or still the literal `.env.example` placeholder — enabling this immediately caught this project's own long-running dev deployment still running `POSTGRES_PASSWORD`/`OPENRBI_SESSION_AGENT_API_TOKEN`/`OPENRBI_AGENT_API_TOKEN` on that exact unedited value; all three were rotated in place (Postgres password changed via `ALTER USER`, no data loss). `POST /auth/login` gained a per-username Redis-backed lockout (10 failures / 15 minutes, generic `429`, new `LOGIN_LOCKED` security event) independent of the existing MFA-challenge attempt cap. `docker/nginx/nginx.conf` also gained baseline TLS-independent security headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`) — HSTS stays deferred to Phase 22, which adds the TLS certificate HSTS depends on. Verified end-to-end against the live stack: full clean restart with every hardening change applied simultaneously, a real sandbox create→start→terminate cycle through the now-non-root-and-capability-stripped session-agent, `ps aux` confirming both nginx services actually run workers as the unprivileged `nginx` user, and the full login-lockout → 429 → window-clear → successful-login cycle.

- Integration/security tests (Phase 21, docs/development.md#tests): a real `backend/tests/` pytest suite (run via `scripts/run-integration-tests.sh`) covering the project brief §30 checklist end-to-end against the live Postgres/Redis/Session Agent — no mocks. 26 tests across auth/MFA (disabled-user login, mandatory MFA enrollment, single-use recovery codes, MFA-reset audit event, the Phase 20 login lockout), authorization/ownership (user A vs. user B's session and quarantine file, including a no-implicit-ownership check for ADMIN), the policy engine (MIME `DENY`, fail-closed unmatched type, forged-domain source rules, conflicting-group precedence, publish/rollback audit events), release tokens (single-use, expiry), and admin session control (a real sandbox isolate/restore/kill cycle via the live Session Agent, `SESSION_ISOLATED`/`SESSION_TERMINATED` audit events, kill correctly restricted to ADMIN). A new `scripts/run-security-tests.sh` covers the remainder that needs the Docker socket or stopping other containers — neither of which the backend has (ADR 0005) — run from the host instead: sandbox network egress (public reachable; Postgres's real IP/cloud-metadata/RFC1918 all blocked), a real Isolate leaving the sandbox with zero attached Docker networks, and a live ClamAV outage correctly surfacing as an error rather than a silent clean result. Surfaced on User Detail as a "Login lockout" status (with a "clears in N min" countdown while locked) and a Lock/Unlock button — deliberately distinct from the existing Disable/Enable (a separate, DB-persisted "account deactivated" state; Lock only blocks *logins*, matching what "locked" already means everywhere else in this system).
- **Roadmap Phase B / B1.10.7 — System Health polling, Audit filters, and final B1.10 documentation pass**: the **System** page now polls `GET /admin/health` every 15s with a visible "Last updated" clock, matching the Dashboard's own pattern, instead of loading once on mount — an admin watching it during an incident no longer has to manually refresh to see a component recover. **Audit** gained a user-ID filter (the backend's `GET /admin/security-events` already accepted `user_id`; the UI just didn't expose it) and an event-type `<datalist>` of every known `SecurityEventType` for autocomplete (suggestions only — the backend remains authoritative on valid filter values, this is not client-side validation), plus the user/session ID columns are now real links to their detail pages instead of unclickable truncated text. Every B1.10.1–B1.10.7 sub-phase's real gaps, corrections, and design decisions are captured in this changelog, [ADR 0018](docs/adr/0018-worker-telemetry-and-health.md), [ADR 0019](docs/adr/0019-metrics-history-and-operations-dashboard.md), `docs/architecture.md`, `docs/security-self-assessment.md`, and `docs/admin-guide.md` — reused and extended throughout rather than written once and left stale, including two documentation corrections found and fixed along the way (a B1.10.2-era security-self-assessment row that had claimed `admin_nodes.py` already shared a dependency it didn't yet have, and this entry itself).

- **Resolution-per-policy — configurable remote-browser screen resolution via SESSION policies**: previously the Xvfb/noVNC resolution was hardcoded (1280×800) in `docker/browser/entrypoint.sh` with no way to change it short of editing the image. `SESSION`-type policies — previously stored but with zero runtime effect (see [policies.md](docs/policies.md#what-a-policys-policy_type-actually-does)) — now carry an enforced `content` field: `{"screen_width": <int>, "screen_height": <int>}`, set through a dedicated width/height editor on the Policy Detail page (shown only for `SESSION`-type policies, never a raw JSON textbox). `app/services/policy_engine.py`'s new `resolve_session_resolution()` reads every published `SESSION` policy attached (via a group) to a session's owner the same way `evaluate_file_action` reads file rules; when more than one applies, the **smallest pixel area wins** (there's no natural "more restrictive" resolution the way `DENY > QUARANTINE > AUTO_RELEASE` is for file actions, so this stays conservative about node resource usage instead). Falls back to the sandbox's own default (1280×800) when no policy applies or a policy's `content` is missing/malformed. The resolution is resolved once at session creation and snapshotted onto two new `BrowserSession` columns (`screen_width`/`screen_height`, migration `a91c4e6b7d3f`) — an already-running session is unaffected by a later policy edit. Threaded end to end: `create_session()` → `session_agent_client.create_sandbox()` → session-agent's `CreateSandboxRequest`/`SandboxConfig` → `DockerSandboxProvider` now passes `SCREEN_WIDTH`/`SCREEN_HEIGHT` container env vars → `entrypoint.sh` reads them with the old hardcoded values as defaults. `SessionResponseDto` now carries the actual resolution so `SecureBrowser.tsx`'s viewer-scaling math (`containFit`) uses the real per-session aspect ratio instead of a hardcoded 1280×800 constant. Also accompanied by two demo `SESSION` policies created and published through the Admin Portal (`Full HD Sessions`, 1920×1080; `Compact / Low-Bandwidth Sessions`, 1024×768) to show the workflow end to end — neither is attached to a group by default.

- **Group↔user↔policy assignment — one Active-Directory-style modal, not separate pages**: the policy engine's `POST`/`DELETE /admin/policies/{policy_id}/groups/{group_id}` attach/detach endpoints existed since Phase 12 with no UI ever calling them, and there was no way at all to add a user to a group from the frontend. Clicking a group now opens one modal with two independent search-and-add panels, **Members** and **Policies**, backed by a new shared `AttachList` component (search → dropdown results → removable rows). New single-relationship `POST`/`DELETE /admin/groups/{group_id}/members/{user_id}` endpoints back the Members panel — the pre-existing `PUT /admin/users/{id}/groups` always replaces a user's *entire* group set, so it can't safely back a single "add this one user" action. The same `AttachList` also backs a mirror-image **Assigned groups** panel on Policy Detail, a quick per-row "Assign to a group" modal on the Policies list, and a live (previously read-only) **Groups** panel on User Detail. `UserSummary.groups`/`PolicySummary.assigned_groups` changed from `list[str]` to `list[{id, name}]` so a detach action has an id to act on, not just a display name.

- **Policy rename, and editing an existing policy's rules without retyping them**: previously a policy's name/description could only be set once, at creation — there was no way to rename one afterwards. New `PUT /admin/policies/{policy_id}` (`app/services/policies.py`'s `rename_policy()`) updates name/description in place (name uniqueness re-checked, `policy_type` deliberately not editable — it determines which enforcement path a policy's content is read by), surfaced via a **Rename / edit description** action on Policy Detail. Separately, starting a new draft version on a policy that already has a published version but no draft yet previously always started from a single blank rule row, silently discarding the currently-published rules from the editor — meaning "editing" an existing rule actually meant retyping every rule from scratch, including the ones left unchanged. `PolicyDetail.tsx`'s `startEditing()` now seeds the new draft's rows/content from the currently-published version instead (the published version itself stays immutable, unaffected) — the action label changes to **"Edit rules (new draft)"** in that case, distinct from **"New draft version"** for a policy with no published version yet, so it's clear which behavior applies.

- **Redis → Valkey** ([ADR 0020](docs/adr/0020-redis-to-valkey.md)): `docker-compose.yml`'s `redis` service now runs `valkey/valkey:8-alpine` instead of `redis:7-alpine`, resolving the RSALv2/SSPLv1 licensing open item flagged in `DEPENDENCIES.md` during Phase 23 (Redis 7.4.10's post-relicense terms needed a legal review before redistribution; Valkey is BSD-3-Clause). Service/hostname, `OPENRBI_REDIS_URL`, and every consumer (`app/core/redis.py`, `app/core/sessions.py`, `app/core/release_tokens.py`, the `redis` health-check component) are unchanged — only the image differs. Every command this project actually uses, including `GETDEL` (single-use release tokens), was individually verified against a real running Valkey container before the switch, not assumed compatible.

- **LDAP group DN matching is now case-insensitive**: previously exact-string comparison (a documented known limitation, `docs/admin-guide.md`/`docs/security-self-assessment.md`), meaning a group->role mapping configured with different casing than the directory actually returns for the identical group — Active Directory in particular is known to normalize DN casing on its own — silently resolved to `USER` instead of the configured role. New `app/core/ldap_dn.py` compares DNs per RFC 4514/4517 (RDN attribute type names and the caseIgnoreMatch-typed attribute values found in real-world DNs are case-insensitive; genuinely different hierarchy/attribute ordering is still correctly treated as a different DN). Regression-tested against a real LDAP server (`test_ldap_login_flow.py::test_group_role_mapping_is_case_insensitive_on_dn`) plus fast unit coverage (`test_ldap_dn.py`).

- **LDAP tests now run automatically in CI**: `scripts/run-ldap-tests.sh` and `scripts/run-ldap-integration-tests.sh` previously only ever ran by hand, unlike every other suite (closed by Roadmap A5 for `run-integration-tests.sh`/`run-security-tests.sh`) — left out deliberately at the time because `run-ldap-integration-tests.sh` restarts the `backend` container mid-run, judged too invasive for the existing `backend-integration-tests` job. New `.github/workflows/ci.yml` job `ldap-integration-tests` runs both against a real, throwaway stack on its own isolated runner VM (no shared state with any other job, so a mid-run backend restart can't affect anything else), torn down unconditionally afterward. The entire LDAP authentication path now has automated regression protection on every push/PR, not just when someone remembers to run the scripts by hand.

### Fixed

- A quota-exceeded session-create attempt was mapped to `502 Bad Gateway` instead of a proper client error — added a dedicated `QuotaExceededError` mapped to `429 Too Many Requests`.
- `POST /admin/policies/{id}/versions/{id}/publish` and `POST /admin/policies/{id}/rollback` 500'd on **every real call** — found while manually clicking "Publish" in the Admin Portal during the resolution-per-policy work above, since no existing test exercised the actual HTTP endpoint (only the underlying service function directly, bypassing the bug). Same root cause already documented below for `Incident.updated_at`: `Policy.updated_at` also has `onupdate=func.now()` (`TimestampMixin`), and both endpoints mutate `policy.current_version_id` then call `db.commit()` before a response-serialization helper does a bare `policy.updated_at` read — triggering the same `MissingGreenlet` from an implicit lazy-load outside the async bridge. The database mutation itself had already succeeded by the time of the crash; only the response serialization failed, so the underlying data was silently correct despite the 500. Fixed with an explicit `await db.refresh(policy)` in both endpoints, same pattern as the earlier fix.
- Two test-cleanup fixtures were missing FK-safe deletion of `group_policies`/`policy_versions.created_by`, both only surfacing once a test actually attached a policy to a group and left it there at teardown: `backend/tests/conftest.py`'s session-scoped `_cleanup_test_data` never deleted `group_policies` at all before deleting `groups`/`policies`, and `scripts/e2e-seed.py`'s `down()` never nulled `policy_versions.created_by` before deleting `users` — both left a dangling FK reference that failed the *next* test run's cleanup (or seed) instead of the run that caused it, making the actual cause easy to miss. Fixed both to match the FK-safe ordering already used elsewhere in each file.
- `BrowserNode` identity was keyed on the Session Agent container's own OS hostname, which is ephemeral and changes on every container recreation — every rebuild during this project's own testing silently orphaned a new `BrowserNode` row instead of updating the existing one (5 accumulated ghost rows found during this pass). Worse, draining a node had no actual effect on scheduling, because the drained row usually wasn't the one `select_node()` was actually looking up anymore. Fixed by giving the Session Agent a configured, stable `node_name` instead of using `socket.gethostname()`.
- Two real, previously-latent bugs in the async database session layer, both surfaced only once Phase 17 happened to make several sequential requests that touched the connection pool and an `onupdate`-triggered column in close succession: (1) `pool_pre_ping=True` is a known-broken combination with SQLAlchemy's async engine — its connection health-check can run outside the greenlet context the async dialect needs, raising `MissingGreenlet`. Replaced with `pool_recycle`, which proactively discards aging connections instead without that failure mode. (2) `Incident.updated_at` has a server-side `ON UPDATE` trigger, which SQLAlchemy marks expired after any flush that touches the row regardless of `expire_on_commit` — a bare attribute access in a response-serialization helper right after `commit()` triggered an implicit lazy-load SELECT outside the async bridge, same `MissingGreenlet` symptom. Fixed with an explicit `await db.refresh()` before serializing. No other response schema currently exposes an `onupdate` column the same way, but this is worth remembering before adding one.
- The Session Agent's write-into-sandbox path (`write_upload`) hit the same tmpfs/archive-API incompatibility Phase 13 found on the read side, plus a second bug: `exec_inspect`'s reported exit code stayed `None` well after the write had actually completed correctly — a plain socket `close()` doesn't reliably signal EOF to the remote process's stdin in time. Fixed by explicitly shutting down the write half of the socket first, and, since the exit code still couldn't always be trusted, independently verifying the write via the file's actual size on disk.
- Docker's archive API (`get_archive`/`docker cp`) cannot read files from a tmpfs mount — confirmed empirically (even a plain `docker cp` from the host failed for a file that unmistakably existed) — since it reads through the storage driver's layer-diff mechanism, and the sandbox's download directory lives under the tmpfs-mounted `/tmp`. Switched the Session Agent's download-fetch to `exec` (`cat`), which reads through a live process in the container's own mount namespace instead.
- `getfattr`'s informational stderr message ("Removing leading '/'...") was getting silently concatenated onto the actual extended-attribute value with no separator, since `exec_run` combines stdout and stderr by default — corrupting the recovered origin URL. Fixed by explicitly redirecting stderr away.
- A background poller task started via a one-off test script died the instant that script's process exited, since `asyncio.create_task` doesn't keep a task alive past its creating event loop closing — the poller only works when a session is created through the actual long-lived server process. Not an application bug, but a real trap for testing background-task-driven features.
- The frontend tried to connect noVNC immediately after `POST /sessions` returned, but the sandbox's VNC server needs a moment after container start to actually begin listening — an intermittent real race condition caught during end-to-end UI testing, not just a theoretical one. Session creation now polls the display port with a bounded retry before reporting the session `ACTIVE`.
- nginx caches the resolved IP of `proxy_pass` upstreams (`backend`, `frontend`) at worker-process start; recreating those containers (e.g. via `docker compose up --build`) without restarting `reverse-proxy` left it pointing at stale, now-dead IPs, causing a `502` on every request. Documented in docs/troubleshooting.md — restart `reverse-proxy` after rebuilding `backend` or `frontend`.
- `components.css`'s `.stat-card` referenced `var(--space-5)`, which the token scale never defined (it jumped straight from `--space-4` to `--space-6`) — found while extending the design tokens for the UI polish pass. Added `--space-5`/`--space-10`.
- The login form's password `<input>` had no accessible name of its own, so browsers computed it from the wrapping `<label>`'s full content — including the show/hide toggle button nested inside it — giving the field the accessible name "Password Show password" instead of "Password", a genuine screen-reader regression, not just a test-tooling quirk. Fixed by giving the input an explicit `aria-label="Password"`, which takes precedence over label-content computation; E2E locators that queried it by label were updated to `{ exact: true }` so they can't also match the toggle button's own "Show/Hide password" label.

### Fixed

- `clamav/clamav:1.3` in `docker-compose.yml` did not exist upstream; pinned to `1.5.4`.
- Several nullable timestamp columns (`recovery_codes.used_at`, `users.disabled_at`, `browser_sessions.started_at`/`ended_at`/`last_activity_at`, `browser_nodes.last_heartbeat`, `policy_versions.published_at`, `quarantine_files.reviewed_at`) were timezone-naive while application code writes timezone-aware datetimes everywhere; this crashed the first time any of them was actually written to.
