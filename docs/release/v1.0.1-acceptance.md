# OpenRBI v1.0.1 Real-Infrastructure Upgrade Acceptance

This is the record of the sprint brief's §10 protocol: a manual v1.0.0 →
v1.0.1 upgrade performed by a human operator against the actual
published GHCR images, on a genuine Linux Docker host (not CI, not a
sandboxed agent environment). `docs/release/v1.0.1-hardening-report.md`
explicitly left this test as **not run** and as the sole remaining GA
precondition — this document is that gap being closed.

Recorded: 2026-08-15
Host: dedicated LAN test machine, freshly provisioned, real Docker Engine,
real `/var/run/docker.sock`
Images under test: `ghcr.io/ley338-gif/openrbi-{backend,session-agent,frontend,browser}:1.0.0` → `:1.0.1-rc.1` → `:1.0.1-rc.2`

## Summary

The test found **three** real, previously-undiscovered P0 bugs that no
amount of CI could have caught, fixed all three, and re-verified all of
them against the real published `v1.0.1-rc.2` images on the same host.

## Second P0 found: no Secure Browser session ever connects on a non-default port

After applying the RBI-POST-023 fix above and completing the full upgrade
protocol (steps 1–6 below), a fresh manual click-through of the real UI —
log in as `testuser`, **Start Secure Browser** — hung forever on
"Connecting display…". The browser's own network panel showed the
display WebSocket opening and immediately closing in a retry loop; server
logs showed every `GET /api/display/{id}/ws` rejected `403 Forbidden` by
the backend, even though the same session, same cookie, and every other
authenticated endpoint worked normally.

Root cause: `app/api/display.py`'s WS handshake compares the client's
`Origin` header against the `Host` header it actually received (a WS
upgrade can't carry the app's normal CSRF header, so this comparison is
the equivalent control — added this same release by RBI-POST-003).
nginx's `$host` variable silently strips a non-default port before
forwarding it; a real browser's `Origin` header never does. On this
deployment's port `8080` — this project's own documented default, not
some unusual configuration — the comparison therefore always failed.
Fixed in `docker/nginx/nginx.conf` and `nginx.tls.conf` by forwarding
`$http_host` instead (RBI-POST-024, [PR #94](https://github.com/ley338-gif/OpenRBI/pull/94)).

This is the same class of gap as RBI-POST-023: correct-looking code,
broken only by real reverse-proxy behavior that no existing test
exercised, because every acceptance script talks to the backend directly
on its internal port and never through the actual proxy. Fixed alongside
a new real end-to-end check in `scripts/fresh-install-acceptance.py` that
opens an actual WebSocket handshake through the real `reverse-proxy`
container going forward.

**Re-verified on the test host.** Applied the same one-line fix directly
to the host's `docker/nginx/nginx.conf` (`Host $host;` → `Host
$http_host;` on the `/api/display/` location), reloaded `reverse-proxy`
(a stock `nginx:1.27-alpine` image with a volume-mounted config — no
rebuild needed), and re-attempted a fresh Secure Browser session as
`testuser` through the real UI. It connected and displayed normally.

Post-upgrade backup/restore verification is the other remaining step
(tracked separately, in progress).

## P0 found: session-agent cannot reach `/var/run/docker.sock` on any real host

**Symptom:** immediately after a clean v1.0.0 install, every attempt to
start a browser sandbox session failed. session-agent logged
`PermissionError(13, 'Permission denied')` against `/var/run/docker.sock`.

**Root cause:** session-agent's container runs as a non-root user (uid
10001) with primary group 0. `/var/run/docker.sock` on a real Docker host
is owned `root:<docker-group>` mode 660, and the docker group's GID is
host-specific — on the test host, `getent group docker` returned
`docker:x:988:sysop`, nowhere near 0. The prior Dockerfile comment's claim
that group 0 "grants socket access without depending on a host-specific
docker-group GID" was simply wrong for real infrastructure. It only ever
appeared correct in CI, because the GitHub Actions runner setup step
separately `chmod 666`s the socket — a workaround explicitly documented in
`ci.yml` as CI-runner-only, which silently masked this bug from ever
being caught before this manual test.

**Fix:** [PR #92](https://github.com/ley338-gif/OpenRBI/pull/92) —
`docker-compose.yml` now requires `OPENRBI_DOCKER_SOCKET_GID` (fails
closed if unset) and adds it as a supplementary `group_add` on
session-agent, resolved at container-start time with no image rebuild
needed. Applied live on the test host as a workaround
(`OPENRBI_DOCKER_SOCKET_GID=988` in `.env` plus the matching
`group_add` line in `docker-compose.yml`) so the rest of this test could
proceed without waiting for the PR to merge, then verified:

```
$ docker compose exec session-agent id
uid=10001(openrbi) gid=0(root) groups=0(root),988
$ docker compose exec session-agent python -c "import docker; c = docker.from_env(); print(c.ping())"
True
```

Because the fix is a runtime `group_add` resolved from an env var rather
than anything baked into the image, it applies equally to the already-
published `v1.0.1-rc.1` images once the host's `docker-compose.yml`/`.env`
carry the fix — no `v1.0.1-rc.2` respin was required for this test.

## Upgrade protocol steps

### 1. Fresh v1.0.0 install

Real GHCR `v1.0.0` images pulled and started via a local
`docker-compose.release.yml` overlay (`image: ghcr.io/ley338-gif/openrbi-{backend,session-agent,frontend}:${OPENRBI_RELEASE_VERSION}`).
All seven services (postgres, redis, clamav, backend, session-agent,
frontend, reverse-proxy) reached `Up`. Alembic migrated a fresh database
to `a8d1f6c42e90`.

**Status: PASS**

### 2. Real test data created through the actual UI

- Bootstrap ADMIN `thomas` created via the real setup wizard
  (`/admin/login` → `SetupFlow.tsx`), with genuine TOTP enrollment and
  recovery codes (not a seeded/scripted account).
- Local `USER` `testuser` created and added to a new group
  `qa-testgroup`.
- A `SOURCE`-type policy `qa-download-policy` created, published as v1,
  with a `QUARANTINE` rule on `*`, assigned to `qa-testgroup`.
- Logged in as `testuser`, started a real Secure Browser sandbox
  session (`baa62d75`) — this is what first exposed the docker.sock P0
  above, before the fix was applied.
- After the fix, the same session start succeeded; a real file
  (`Get_Started_With_Smallpdf.pdf`, 67.6 KB) was downloaded inside the
  sandbox. It was scanned (`CLEAN`) and, per the policy above, landed as
  a genuine `QUARANTINED` item — not synthetic seed data.
- Session ended cleanly; confirmed via
  `docker ps -q --filter label=openrbi.managed=true` returning empty
  that session-agent tears down containers correctly, not just creates
  them.

**Status: PASS**

### 3. Pre-upgrade backup

Real `scripts/backup.sh` run against the live v1.0.0 stack (not a
throwaway/test invocation): `openrbi-db-20260815T154033Z.sql.gz` (12K)
and `openrbi-quarantine-20260815T154033Z.tar.gz` (64K), both non-empty
and archived off-host before the upgrade began.

**Status: PASS**

### 4. Upgrade to v1.0.1-rc.1

`OPENRBI_RELEASE_VERSION` bumped to `1.0.1-rc.1`; all four real published
images (backend, session-agent, frontend, browser) pulled from GHCR.
Containers stopped with volumes retained (`down`, no `--volumes`),
Postgres/Redis/ClamAV brought back up, and Alembic run against the new
backend image:

```
Running upgrade a8d1f6c42e90 -> 112d0613aefc, add LDAP_CONFIG_READ security event
```

Single head, no drift. Full stack brought up on the new images; all
seven containers reported `Up` running
`ghcr.io/ley338-gif/openrbi-*:1.0.1-rc.1`. session-agent's `id` on the
upgraded stack confirmed `groups=0(root),988` — the fix persists across
the upgrade because it lives in `docker-compose.yml`/`.env`, not the
image.

**Status: PASS**

Logged in fresh as `thomas` (a stale pre-upgrade CSRF token correctly

Reverse proxy and both portals responded (`/`, `/admin/`) after the

**Status: PASS**

### 6. Post-upgrade backup/restore

Real `scripts/backup.sh` run again against the upgraded (`v1.0.1-rc.1`)
stack: `openrbi-db-20260815T160146Z.sql.gz` (15K),
`openrbi-quarantine-20260815T160146Z.tar.gz` (64K). Live state was then
deliberately corrupted (not simulated): `testuser` renamed to
`corrupted` via a direct `UPDATE`, and the quarantined file's bytes
deleted from `/app/data/staging/`. The real production
`scripts/restore.sh` was then run — including its interactive
confirmation prompt — against the post-upgrade backup:

- Restore stopped `backend`/`session-agent`, replaced quarantine
  storage, restored the database (`--clean --if-exists` drop/recreate),
  restarted services, and ran its own post-restore reachability checks
  with zero warnings.
- `SELECT username FROM users` afterward showed `thomas`/`testuser` —
  the corruption was reverted, not merely "some data present".
- The quarantine file was back at
  `/app/data/staging/abce4555...`, and `sha256sum` on it matched its
  own content-addressed filename exactly — a byte-exact restore, not a
  best-effort one.
- `/health` and `/admin/` both responded after restore.

(Restore.sh's `compose()` helper hardcodes `-f docker-compose.yml` only,
without the local `docker-compose.release.yml` overlay used to run the
published images in this test. Its `compose run` step for quarantine
restore would otherwise resolve `backend` to a locally-built image
instead of the actual `1.0.1-rc.1` image under test. Worked around by
temporarily adding matching `image:` lines directly under `backend`/
`session-agent` in `docker-compose.yml` for the duration of this test.
Real deployments following the documented `docs/deployment.md#update-
procedure` build from source into `docker-compose.yml` directly and are
unaffected — this is specific to validating published-image RCs.)

**Status: PASS**

## Outcome

The real upgrade path — actual GHCR images, actual Linux Docker host,
actual UI-driven admin/user actions, a genuine downloaded/scanned/
quarantined file, a genuine pre- and post-upgrade backup/restore cycle
with deliberate corruption and byte-exact verification — preserves all
state and functionality across the v1.0.0 → v1.0.1-rc.1 upgrade, once the
session-agent docker.sock fix
([PR #92](https://github.com/ley338-gif/OpenRBI/pull/92)) is applied. That
fix was found by, and only by, this real-infrastructure test — the
project's entire existing CI suite (including its own `Upgrade
acceptance` gate) passed throughout the whole sprint without ever
exercising this failure mode, because the CI runner's `chmod 666`
workaround on `/var/run/docker.sock` hides it.

All six steps of the sprint brief's §10 protocol are now complete and
passing. This closes the sole remaining GA precondition named in
`v1.0.1-hardening-report.md`.

## Third finding: Admin Portal had no client-side role check

Spotted by the operator directly, continuing to click through the real
UI as `testuser` after the two fixes above: navigating to `/admin/`
showed the full admin shell (sidebar, nav) before failing to load its
dashboard data with a generic "Could not load the operations dashboard"
error. Backend authorization was never actually bypassed — every real
admin endpoint already denies a `USER`-role session — but the client
shouldn't have let a non-privileged session into the shell at all.

Root cause: `RequireAuth` (`frontend/admin/src/App.tsx`) checked only
whether a session existed, never its role. Fixed to check for
`ADMIN`/`SECURITY_REVIEWER` and redirect anything else to the User
Portal (RBI-POST-025, [PR #95](https://github.com/ley338-gif/OpenRBI/pull/95)).

## Cutting v1.0.1-rc.2 and re-verifying all three fixes on the real published images

`v1.0.1-rc.1`'s tag predates all three fixes above and is immutable
(RBI-POST-004), so `v1.0.1-rc.2` was cut to actually carry them —
version bump ([PR #93](https://github.com/ley338-gif/OpenRBI/pull/93)),
both fixes merged to `main`, a fresh full `Release gates` run on the
exact merge commit (`9cabf00e772109d32ac1ca5a2feb117e0fa00e3e`), a
dry-run release build, then the real publish: four images pushed to
`ghcr.io` with real registry manifest digests, a real GitHub prerelease
tag targeting that exact commit.

Pulled and cut over to the real published `v1.0.1-rc.2` images on the
same LAN test host (not a rebuild from source):

- `session-agent`'s `id` after the cutover still showed
  `groups=0(root),988` — the docker.sock fix persists across an
  image swap because it's `docker-compose.yml`/`.env` configuration, not
  anything baked into the image.
- A fresh Secure Browser session as `testuser` connected and displayed
  normally (RBI-POST-024 fix confirmed against the real published
  image and the real `nginx.conf` fix on this host).
- Navigating to `/admin/` as `testuser` in a fresh private browser
  window redirected straight to the User Portal, never showing the
  admin shell (RBI-POST-025 fix confirmed against the real published
  frontend image). Note: an already-open tab from before the cutover
  initially appeared to still show the old behavior — browser-side
  caching of the previous JS bundle, not a fix failure; a fresh
  session showed the correct redirect immediately.

**Status: PASS.** All three real-infrastructure findings from this
protocol are fixed, merged, published as `v1.0.1-rc.2`, and confirmed
working end-to-end against the actual published images on real
infrastructure — not just in CI.
