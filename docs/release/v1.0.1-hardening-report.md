## Security regression result

Every fix's own PR ran the full existing CI suite (backend/LDAP/fresh-install/backup-restore/upgrade acceptance, Trivy image scans, dependency scans, secret scanning, lint/type-check) and passed before merge — this *is* the project's existing security regression suite, and it stayed green (or was fixed until it was) through all thirteen merges. The specific checklist in the sprint brief's §9 maps onto that suite's existing coverage (auth/MFA/LDAP/sandbox/network/files scenarios) plus the CSRF-specific cases added in RBI-POST-003's own test file.

**Not independently re-run as a single end-to-end pass in this sprint** beyond what each PR's CI already exercised — see "Remaining P0/P1" below for what that means for GA readiness.

## v1.0.0 → v1.0.1 upgrade result

**Not run.** The sprint brief's §10 protocol (install a real v1.0.0, seed real data, back up, upgrade to a v1.0.1-rc.1, verify every subsystem, back up/restore again) requires a genuine Linux Docker host with root access to run `scripts/setup-network-isolation.sh` and the acceptance scripts for real — this session ran in a sandboxed environment without that. `scripts/run-upgrade-acceptance.sh` already exists and is wired into CI (and passed, unmodified in its logic, on every PR in this sprint via the `Upgrade acceptance` gate) — but that CI run upgrades *within* the current checkout's history, not from the actual tagged `v1.0.0` GHCR images through a real `v1.0.1-rc.1` tag, which is what §10 specifically asks for.

## Backup/restore result

Same caveat as above: `scripts/run-backup-restore-acceptance.sh` passed on every PR via CI's `Backup and restore acceptance` gate (real backup, real deliberate corruption, real restore, exact record/byte comparison) — but that's the existing acceptance suite running in CI, not a manual run against a real host as part of this sprint specifically.
