## Security regression result

Every fix's own PR ran the full existing CI suite (backend/LDAP/fresh-install/backup-restore/upgrade acceptance, Trivy image scans, dependency scans, secret scanning, lint/type-check) and passed before merge — this *is* the project's existing security regression suite, and it stayed green (or was fixed until it was) through all thirteen merges. The specific checklist in the sprint brief's §9 maps onto that suite's existing coverage (auth/MFA/LDAP/sandbox/network/files scenarios) plus the CSRF-specific cases added in RBI-POST-003's own test file.

After the final hardening merge, the complete CI workflow was independently re-run as a single `push` validation on final `main` commit `04a73a2fae9f69960136370bc540ff81fb9bf2dc`. Workflow run `31877886432` completed successfully, including the aggregate `Release gates` job and all required integration, acceptance, dependency, secret, and image-scanning jobs. The release-version commit must receive its own equally complete green run before RC publication; results do not transfer between commits.

## v1.0.0 → v1.0.1 upgrade result

**PASS, real infrastructure** — see [`v1.0.1-acceptance.md`](v1.0.1-acceptance.md)
for the full record. A manual operator, not CI, ran the sprint brief's
§10 protocol end-to-end against the actual published `v1.0.0` and
`v1.0.1-rc.1` GHCR images on a genuine Linux Docker host: a real fresh
install, real UI-driven test data (admin bootstrap, a local user, a
group, a published policy, and a genuine downloaded/scanned/quarantined
file), a real pre-upgrade backup, a real upgrade, full data/functional
verification post-upgrade, and a real post-upgrade backup/restore cycle
with deliberate corruption and byte-exact verification. This test is
what actually caught RBI-POST-023 below — something the existing
`scripts/run-upgrade-acceptance.sh` CI gate could not have caught, since
it upgrades *within* the current checkout's history on a CI runner whose
docker.sock is `chmod 666`'d as a documented runner-only workaround,
masking exactly this failure mode.

## Backup/restore result

Both a pre-upgrade and a post-upgrade backup/restore cycle were run for
real as part of the test above (real `scripts/backup.sh` and
`scripts/restore.sh`, including a deliberate corruption of live data and
a byte-exact SHA-256 verification after restore) — see
[`v1.0.1-acceptance.md`](v1.0.1-acceptance.md). Aside from that,
`scripts/run-backup-restore-acceptance.sh` continues to pass on every PR
via CI's `Backup and restore acceptance` gate (real backup, real
deliberate corruption, real restore, exact record/byte comparison).
