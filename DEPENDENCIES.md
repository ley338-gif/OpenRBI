# Dependencies

This document tracks the central third-party components OpenRBI relies on: what they do, why they were chosen, their license, and possible alternatives. Versions and licenses are verified against the actual pinned version in use, not assumed from memory — update this table whenever a dependency's pinned version changes.

| Component | Purpose | Version (pinned) | License | Project URL | Why used | Alternative considered |
|---|---|---|---|---|---|---|
| Firefox ESR | First `BrowserProvider` implementation; renders isolated web sessions server-side | `140.13.0esr` (Debian package `firefox-esr` on `debian:bookworm-slim`, see `docker/browser/Dockerfile`) | MPL-2.0 | https://www.mozilla.org/firefox/ | Mature remote-control/automation support, strong sandboxing primitives, ESR channel gives predictable patch cadence | Chromium (planned second provider) |
| noVNC | First `DisplayProvider` implementation; browser-based VNC client, no plugin required | `@novnc/novnc ^1.7.0` (`frontend/package.json`) | MPL-2.0 | https://github.com/novnc/noVNC | Pure JS/HTML5, no native client install, widely deployed, easy to audit | KasmVNC, Guacamole |
| Xvfb + x11vnc | Virtual X11 display and VNC server running inside the browser sandbox container | Debian `bookworm` package versions (`xvfb`, `x11vnc 0.9.16-9`), see `docker/browser/Dockerfile` | MIT (Xvfb, part of X.Org) / GPL-2.0 (x11vnc) | https://www.x.org/ / https://github.com/LibVNC/x11vnc | Lightweight, well understood, well-proven Xvfb+x11vnc pairing for headless browser display | TigerVNC's combined Xvnc server, KasmVNC-integrated capture |
| ClamAV | First `FileScanner` implementation; open-source antivirus engine for downloaded/uploaded files | `1.5.4` (`clamav/clamav:1.5.4`) | GPL-2.0 | https://www.clamav.net/ | Open source, actively maintained signature DB, daemon (`clamd`) mode fits the fail-closed scan pipeline | Commercial AV engines (ICAP-compatible) |
| PostgreSQL | Primary relational store for users, policies, sessions, audit, quarantine metadata | `16` (`postgres:16-alpine`, `docker-compose.yml`) | PostgreSQL License (permissive) | https://www.postgresql.org/ | Strong relational + JSONB support, mature migration tooling, widely operable | MySQL/MariaDB |
| Redis | Transient state: server-side sessions, MFA/login-lockout state, release tokens | `redis:7-alpine` (`docker-compose.yml`) resolves to **`7.4.10`** as actually pulled/verified in this environment | **RSALv2/SSPLv1 dual license** (Redis Ltd, post-7.4 relicense — confirmed applicable, this is not the older BSD-3-Clause version) — **legal review needed before any redistribution/commercial use of OpenRBI as-is; switching the pinned image to Valkey is the straightforward fix if that's a blocker** | https://redis.io/ | Fast transient store with pub/sub and TTL primitives well suited to session/lockout state | **Valkey** (BSD-3-Clause fork, drop-in compatible) |
| gVisor (optional, not implemented) | Additional sandboxing runtime for a future `GVisorSandboxProvider` | Not built in MVP 1 — only `DockerSandboxProvider` exists (see [ADR 0010](docs/adr/0010-docker-sandbox-provider.md)); the `SandboxProvider` interface doesn't block adding it later | Apache-2.0 | https://gvisor.dev/ | Userspace kernel reduces syscall attack surface vs. plain runc | Kata Containers (heavier, VM-based) |
| Docker Engine | Baseline container runtime via `DockerSandboxProvider` and Session Agent | Host-provided; verified against Docker Engine `29.6.2` during this project's development | Apache-2.0 | https://www.docker.com/ | Ubiquitous, well-documented API (`docker-py`), fits single-host MVP | Podman |
| FastAPI | Backend/API and Session Agent web framework | `>=0.115` (`backend/pyproject.toml`; `0.141.1` installed) | MIT | https://fastapi.tiangolo.com/ | Async-first, typed request/response models via Pydantic, good fit for an internal authenticated API plus public REST API | Django REST Framework |
| SQLAlchemy + Alembic | ORM and schema migrations | SQLAlchemy `>=2.0` (`2.0.52` installed), Alembic `>=1.13` (`1.19.1` installed) | MIT | https://www.sqlalchemy.org/ | Mature, explicit migration story required by this project's "migrations are mandatory" rule | Prisma (Python support immature) |
| pyotp | TOTP generation/verification | `>=2.9` (`backend/pyproject.toml`; `2.10.0` installed) | MIT | https://github.com/pyauth/pyotp | Small, well-audited, RFC 6238 compliant | python-otp alternatives |
| python-ldap | `LdapAuthProvider` (Roadmap Phase B / B1.2, docs/adr/0015) — LDAP/LDAPS bind authentication | `>=3.4` (`backend/pyproject.toml`; `3.4.7` installed) | Python Software Foundation License (permissive) | https://www.python-ldap.org/ | Bindings against the native OpenLDAP C library — mature, widely deployed, direct LDAPS/StartTLS support. Compiles against `libldap-dev`/`libsasl2-dev` at build time only (`backend/Dockerfile` purges them after `pip install`, keeping only the runtime `libldap2`/`libsasl2-2` shared libs in the final image) | `ldap3` (pure Python, no native compile step, but python-ldap's direct C-library bindings and long production track record against real AD deployments were preferred for this specific use) |
| React + TypeScript + Vite | Admin/user frontend (currently just the noVNC test harness — see [architecture.md#status](docs/architecture.md#status)) | React `^19.2.8`, TypeScript `~6.0.2`, Vite `^8.2.0` (`frontend/package.json`) | MIT | https://react.dev/ | Component-driven UI, strong typing, fast dev loop | Vue, Svelte |
| nginx | Reverse proxy: routing, WebSocket relay, TLS termination (production overlay) | `1.27-alpine` (`docker-compose.yml`) | 2-clause BSD-like (nginx license) | https://nginx.org/ | Mature, well-understood WebSocket/TLS support, minimal footprint | Caddy, Traefik |

**Confirmed during Phase 23's documentation review, not assumed:** `redis:7-alpine` as pinned in `docker-compose.yml` was checked with `redis-server --version` inside the actual running container and resolves to **Redis 7.4.10**, which is under Redis Ltd's post-relicense **RSALv2/SSPLv1** dual license, not the older BSD-3-Clause terms. This is a real open item, not a hypothetical one — get a legal opinion on whether that's acceptable for how this project intends to be distributed/used before a real release; switching `docker-compose.yml`'s `redis` image to a Valkey tag (drop-in compatible, BSD-3-Clause) is the straightforward mitigation if it isn't.
